# Миграции схемы базы данных

Каждый файл миграции — это набор SQL-команд, которые применяются один раз
и больше не повторяются. Состояние применённых миграций отслеживается
в служебной таблице `schema_migrations` внутри самой базы.

## Правила именования файлов
V<NNN>__<short_description>.sql
- `V` — фиксированный префикс.
- `<NNN>` — порядковый номер из трёх цифр (`001`, `002`, ..., `999`).
  Номера НЕ переиспользуются. Если миграция была применена хоть на одной
  машине — её файл больше нельзя редактировать, нужна новая миграция со
  следующим номером.
- `__` — два символа подчёркивания.
- `<short_description>` — краткое описание в `snake_case`, латиницей.

Примеры допустимых имён:
V001__initial.sql
V002__rtcm.sql
V003__add_pdop_to_epochs.sql
V004__drop_unused_session_field.sql
## Содержимое файла миграции

- Только SQL-команды, без транзакционных директив (`BEGIN`, `COMMIT`,
  `ROLLBACK`) — Модуль миграции сам оборачивает каждый файл в транзакцию.
- Допустимо использовать `IF NOT EXISTS` / `IF EXISTS` для команд, которые
  могут быть применены к разным состояниям схемы.
- Комментарии — желательны: что и зачем делает миграция.
- Имена ограничений (`CONSTRAINT name CHECK ...`) — желательны, чтобы их
  можно было адресовать в будущих миграциях.

## Что нельзя делать

- Менять содержимое уже применённой миграции. Если что-то нужно исправить —
  новая миграция со следующим номером.
- Удалять файлы применённых миграций. Модуль миграции будет ругаться на
  несоответствие записей в `schema_migrations` файлам на диске.
- Использовать DDL-команды, требующие пользовательских прав суперпользователя.
  Все миграции должны проходить под обычной ролью приложения (`ntrip_app`).

## Применение

```bash
python -m ntrip_accuracy_monitor.persistence.migrator --config config.toml
```

Модуль миграции прочтёт каталог `migrations/`, сравнит со служебной таблицей
`schema_migrations` в базе и выполнит недостающие миграции в порядке номеров.
Каждая миграция применяется в отдельной транзакции — при ошибке откатывается
только текущая миграция, ранее применённые остаются в базе.

Откат миграций НЕ поддерживается. Если миграция изменила схему так, что
её нужно «откатить», пишется новая миграция со следующим номером,
которая возвращает схему в прежнее состояние.
